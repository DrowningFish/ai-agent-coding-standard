# API 设计规范

## 总体原则

- API 设计必须面向业务能力，而不是数据库结构
- 接口命名统一、调用方式清晰、返回结构稳定
- 错误处理统一、可追踪、可排查
- 不把内部实现细节直接暴露为外部接口

## 命名规范

- URL 使用名词复数或资源型命名，避免动词混入
- 采用 REST 风格，必要时支持 `GET/POST/PUT/DELETE`
- API 版本可通过路径或请求头控制，如 `/api/v1/order`

示例：

```http
GET /api/v1/orders/{id}
POST /api/v1/orders
PUT /api/v1/orders/{id}
DELETE /api/v1/orders/{id}
```

## 请求与响应结构

### 通用响应

```json
{
  "code": "200",
  "message": "success",
  "data": {}
}
```

### 错误响应

```json
{
  "code": "40001",
  "message": "参数校验失败",
  "data": null
}
```

## 参数校验

- 必填参数必须校验
- 字段长度、格式、枚举值必须明确限制
- 对于敏感信息，统一做脱敏策略
- 入参校验优先在后端进行，不依赖前端校验

## 错误码设计

- 规范化错误码，区分客户端参数错误、鉴权失败、业务冲突和系统错误
- 错误码保持稳定，避免随意新增无业务含义的编码

建议：

- 200：成功
- 400xx：客户端参数错误
- 401xx：认证/授权错误
- 409xx：冲突、重复、状态异常
- 500xx：系统错误

## 安全约束

- 认证和授权必须在网关或后端统一处理
- 敏感操作必须校验权限和日志埋点
- 不允许直接返回堆栈信息或内部异常明文

## 接口文档

- 接口文档必须与实际实现一致
- 重要接口必须写明请求参数、返回结构、异常场景
- 对于复杂接口要说明请求流、状态迁移和错误补偿

## 调用链治理

- 外部依赖必须统一封装，并设置超时和重试策略
- 对第三方调用要记录失败日志和监控指标
- 对关键链路要写清楚熔断、降级和补偿机制
