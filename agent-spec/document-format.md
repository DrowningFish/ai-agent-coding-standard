# 项目文档约定

只在业务任务确需记录时使用；维护模板本身不生成业务文档。默认一项大需求一份固定文档，小改动在项目changelog持续追加；这些规则约束文件数量，不只是要求内容少写。沿用既有位置和文件名，不因示例补建目录。

## 内容归属，而非建文件清单

| 位置 | 需要记录的内容 |
| --- | --- |
| 一项大需求的固定文档 | 目标/范围/规则与验收、必要设计和取舍、实施状态、相关问题/审查结论、验证摘要及交付引用，均在同一文件相应位置更新 |
| 项目changelog | 普通小改动的日期、原因、实际修改和必要检查，一条或合并连续沟通记录即可；有关联时链接固定需求 |
| 已有总需求、架构、接口或项目约束 | 只回补本次实际失效的公共内容；总需求保留整体有效说明，详细设计和执行证据引用固定需求，不重复复制 |

大需求按影响及设计必要性判断，不按一次消息或代码行数判断。同一需求的补充、修复、审查和测试均继续原文件，不新建带日期、阶段、角色或包号的平行文档。简单项目可由一份文档承担整体需求与当前需求记录；不为套表另建总需求、架构或进度文档。

## 固定需求文档如何更新

- 使用稳定文件名和需求标识，后续会话按原目标找到原文件；不每次另建“补充方案”“整改说明”“交付说明”“测试报告”。内容超长先压缩重复叙述、引用代码及原始结果，不自动按阶段拆文件。
- 按需组织范围与验收、设计、状态/问题、验证/交付等内容，无需固定章数或空栏目。一个问题在原位置维护当前状态，重要变更用短修订摘要追溯，不把聊天或每次执行流水逐段追加成历史堆栈。
- 验证只记录本次选测依据、版本/环境、关键命令或场景、结果及未覆盖范围；测试脚本、CI记录和原始产物用引用，不把它们复制造成多份报告。测试设计、实际执行与验收结论仍明确区分，但不因此拆文件。
- 长任务状态、审查问题及交接检查点维护在同一文件对应位置，已解决项关闭或压缩；没有持续状态需要时不添加。changelog只放摘要与引用，不再复制整份设计或测试结果。

## 独立文件的例外

- 用户明确要求独立方案、完整测试文档或外部报告，或项目明确的强制交付/合规要求时，才按指定范围另建；不把“需要设计/测试/交接”本身当例外。能直接用原需求文档满足指定交付时不复制一份。
- 明确要求的产物可包含必要清单和安装/迁移说明，遵循[delivery.md](delivery.md)；包内说明不意味着在项目changes目录再建一份带包号的交付文档。
- 现有独立权威架构/API说明、用户已指定的资料继续沿用，不因本规则擅自合并或删除。已经分散的历史资料先识别当前入口并停止新增；实际归并、移动和删除须有对应授权，不能凭文件名或截图判定内容重复。
- Git保存修订历史，不默认生成history快照；无Git且确有追溯需要时保留必要版本，不复制每次聊天。不能归档唯一完整有效需求后，只留下碎片化变更索引。

## 写法

- UTF-8、简体中文，每份文档一个一级标题，章节不跳级；代码标识符和命令保持原文。
- 已确认、计划、实现、验证和待确认明确区分。填写提示不是事实或执行命令；无此要求写“不适用”，未知不能写“已通过”或“无风险”。
- 链接指向现有资料，详细规则只维护一处。文档记录决定及原因，不复制整个聊天或日志，也不保留凭据。
- 已确认变化写清改了什么、为什么改、如何改；在原需求文件更新，只回补已有总需求、架构、接口中真正失效的公共部分，不因“记录完整”新增文件或重复正文。
- 当前规则失效时只回补受影响内容；历史决定和失败证据保留并关联后续变化，不重写成新规则一直存在。
- 初始需求草稿确认后仍在原文件持续维护，简单项目可同时作为总需求；开始实施不自动归档唯一完整说明。既有history资料标明已被替代及当前入口，不作为最新功能说明，也不据此继续复制新快照。
- 总需求按功能组织，不按对话日期堆叠。可以链接子需求细节，但必须保留整体功能说明；已确认未实现与已验收分别标识。README只作使用及导航，不用changes索引或架构文档替代总需求。
