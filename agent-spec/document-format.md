# 项目文档约定

只在业务任务确需记录时使用；维护模板本身不生成业务文档。沿用项目既有位置，不因示例文件名补建整套目录。

## 记录什么

| 资料 | 需要记录的内容 |
| --- | --- |
| 当前总需求 | 项目目标、范围、角色、全部已确认功能及核心流程、共同规则和验收口径；独立可读，状态与实现分开 |
| 单项需求/changes | 本次新增或改变的内容、原因、影响与验收，关联并回补总需求；不代替总需求 |
| 方案/架构 | 如何实现、技术取舍和设计影响；局部方案留在对应需求，不混入整份讨论或测试流水 |
| 问题/changelog | 原因、实际修改及检查；小修一条即可，已有问题记录直接沿用 |
| 验证结果 | 日期、版本/环境、实际命令或场景、结果与未覆盖范围 |
| 进度/交接 | 长任务的当前范围、决定、证据位置、未完成和下一步；结束后关闭 |
| 项目约束 | [project-rules.md](project-rules.md)中的有效特别要求、状态及来源 |

讨论不默认写文件，单份方案只写指定内容和必要导航。何时升级记录见[workflow.md](workflow.md)，不对每次对话创建需求编号。

## 写法

- UTF-8、简体中文，每份文档一个一级标题，章节不跳级；代码标识符和命令保持原文。
- 已确认、计划、实现、验证和待确认明确区分。填写提示不是事实或执行命令；无此要求写“不适用”，未知不能写“已通过”或“无风险”。
- 链接指向现有资料，详细规则只维护一处。文档记录决定及原因，不复制整个聊天或日志，也不保留凭据。
- 新需求或重大关联变化需要说明时，记录背景、范围/规则变化、影响、必要设计和验收结果；按实际复杂度组织，不强制七章齐全。
- 已确认变化写清改了什么、为什么改、如何改，回补受影响的总需求、架构、计划及验收预期中已失效的部分；不为凑清单新建无关文件。重要实施变化在项目已有变更索引/changelog保留日期、摘要及必要关联，小修只简记，不按每次对话重复立项。
- 当前规则失效时只回补受影响内容；历史决定和失败证据保留并关联后续变化，不重写成新规则一直存在。
- 初始需求草稿可在原文件中持续修订，确认后作为当前总需求继续维护；开始实施不自动归档唯一完整需求。history仅存确有价值的旧版本/讨论，标明已被替代及当前入口，不作为最新功能说明。
- 总需求按功能组织，不按对话日期堆叠。可以链接子需求细节，但必须保留整体功能说明；已确认未实现与已验收分别标识。README只作使用及导航，不用changes索引或架构文档替代总需求。
- 测试方案定义如何验收，执行报告记录实际结果，Agent交接说明授权和任务边界；不把三者混成一套完成条件。
