# 按需工作流程

本文件统一任务分流、项目接入、实施和交接；只读当前任务需要的部分。它不是每次对话必须走完的清单，安全与协作边界见[security.md](security.md)。

## 1. 分流与规模

- 讨论、解释和评审只回答；生成方案只维护指定文档，不默认实现、测试、立项、更新进度或打包。方案完成不等于执行验收完成。
- 小BUG、局部优化和微调：相关上下文→最小修改→必要检查→项目changelog简记。不新建需求、计划、测试方案或检查点；同一问题的连续沟通可合为一条记录。
- 涉及多条路径、共享模块、并发或性能，但目标不变的修复：沿原需求补必要影响、设计和验证，不因为代码多就新建需求。
- 独立目标或业务规则、公共接口、数据、权限实质变化：修订原需求或新建关联说明，明确验收和兼容性后按范围实施。
- 任务执行中发现风险扩大再补充必要步骤，不倒补整套形式材料。项目明确针对该类任务要求的检查和交付继续执行。

规模依据影响、风险及一致性判断，不按消息、文件或代码行数。分类明确时直接工作，不固定输出分类表或再次批准。

## 2. 接入与项目约束

- 新项目先明确目标、使用者、最小可用版本的一条可独立完成的核心路径和已知硬限制，不提前塞入后续功能；只问会改变当前结果的事项，不强制首轮完成技术选型或整张问卷。
- 已有项目按任务需要只读核实构建/锁文件、相关代码、CI及有效文档。需要了解变更背景时再看Git历史，不默认全库扫描。
- 已有入口和项目约束先比较合并；保留有效规则，不以空模板覆盖，不启动历史整改、框架迁移、全量注释或旧文档重写。
- [project-rules.md](project-rules.md)由用户直接填写或Agent在需要时补全，已有权威规则可链接引用。工程事实注明来源，用户决定注明确认来源；从构建文件发现命令不等于授权其副作用。
- 当前技术栈、接口、formatter和命令以工程核实为准。未选择技术栈不能当作沿用默认；明确项目选择可覆盖通用技术默认值。
- 只有当前工作依赖的缺失信息才询问；环境、数据、提交、外部写入等授权不可从配置或历史推断。未经确认的建议不写为有效要求；不为普通讨论自动修改约束文件。

## 3. 需求归属与长期记录

- 有持续功能演进的项目应有一份当前有效的总需求说明：已有完整文档直接沿用，没有时在形成已确认需求时整理一份，不预建整套资料。它应独立说明项目目标、范围、角色、全部已确认功能及核心流程、共同业务规则、限制和验收口径，不能只有changes/history的链接目录。详细子需求和方案按需链接，不把逐次对话原文拼成总需求。
- 初始沟通围绕同一份需求草稿逐步改写、补全和消除矛盾，明确已确认与待确认；进入实施时将它继续维护为当前总需求。不因开始编码或生成第一份changes就把唯一完整需求移入history，再用简短变更摘要代替。
- 未达到已确认验收标准是BUG，沿原需求/问题修复。规则不明确时先澄清，改变规则时记录变化、原因和影响；一次新对话不是一次新需求。
- 当前需求、架构、接口及验收预期保持有效，后续规则替代前面的规则时只回补失效部分；保留旧决定和测试证据，并关联新修订。
- 总需求描述“现在确认要做什么”，单项需求/changes描述“这次新增或改变什么”，方案/架构描述“如何实现”，执行记录描述“实际上完成并验证了什么”。每次确认新能力或改变规则时，同步修订总需求中受影响的模块、流程和共同规则，再关联单项说明；纯实现修复不改变需求时无需改写总需求。
- 总需求保留已确认但尚未实现的范围，用简短状态或链接区分待实现、已实现待验收和已验收；不因代码尚未完成而删除需求，也不从现有代码反推并覆盖用户已确认目标。未确认设想单列待决，不混入有效规则。
- history只保存确有追溯价值的旧快照、废弃方案或讨论证据，归档前确认有效内容已进入当前总需求并标明当前入口。未归档草稿可以直接修订；已明确作为历史快照的文件不静默改写为最新规则。若唯一完整需求误放history，应整理/恢复为当前文档，历史保留原意并补替代链接，不让读者靠遍历历史还原当前功能。
- 项目已有文档直接沿用，文件名不限。不要求固定创建requirements、architecture、development-plan、test-plan、PROGRESS等整套资料。
- 长期项目需要时，用现有导航记录需求标识、当前说明、状态及关联问题/变更；任务仅跟踪活跃工作，结束后关闭，不为每项需求保留永久Agent。
- 新能力或重大变更记录必要目标、范围、规则、设计影响、验收和结果；局部修复只简记原因、修改与检查。记录详细信息只维护一处。

总需求维护全局功能及共同规则，子需求补充局部细节，避免整段重复。README提供用途、接入和总需求入口，不代替需求基线；架构文档保留实现选择，不成为需求和测试结果的混合容器。多份资料冲突时回到最新已确认决定核实，不以文件名或更新时间自动判定正确。

### Agent主动发现上下文与影响

用户通常从整体产品描述目标，不会主动指出一个月前的功能、依赖或历史取舍。关联识别是Agent的工作，不要求用户先整理上下文包、列受影响模块或判断资料是否过期。按以下过程自行查找，简单改动缩小范围，不每轮生成分析报告：

1. 从本轮目标提取业务对象、行为和规则，查当前总需求及已有功能导航，判断是延伸旧功能、修复、规则修订还是独立能力；不能因对话是新的就按全新功能设计。
2. 定位对应入口、定义及测试，沿上游调用方和下游依赖双向核查；特别关注共同数据、状态流转、权限、事务、缓存、配置、异步任务和外部接口，避免只看准备修改的文件。
3. 涉及共用能力、旧行为不清或方案理由未知时，检索相关需求/设计、问题及变更；有Git时按路径、符号或变更内容查必要历史，无Git时比较现有资料。时间久远不表示规则失效，搜索不到也不表示能力或依赖不存在。
4. 对检索结果核实版本和适用范围：文档说明确认目标，代码反映当前实现，测试提供有限行为证据；代码与需求不一致时标出差异，不能直接把代码当成新的业务规则。摘要、索引和检索结果只提供线索，关键决定回到原始资料核实。
5. 在方案或实施记录的现有位置简记已关联功能、相关路径/契约、不可破坏约束、验证范围和仍未知事项。已有资料用路径及必要章节引用，不复制全部历史，不另外建立固定格式的上下文台账。

发现关联时可直接说明“此需求延伸已有A能力，将复用B并核查C调用方”，不让用户再次确认代码可核实的关系。只有确实存在业务冲突、关键取舍或无法取得且会影响结果的信息，才提出具体问题，并说明已核查的事实和选择影响。范围/授权变化仍按入口约定处理。

方案及编码前应已定位相关旧能力、主要调用路径和已知共享约束，并明确未核实范围；审查再从调用方和验收标准独立检查遗漏。这是按风险执行的检查，不保证静态检索能发现所有运行时依赖，也不要求预先扫描全库或读取全部历史。

项目已有IDE引用查找、代码索引或调用图时可以辅助发现，使用前核实其覆盖范围和代码版本；没有这些工具时用文本/符号搜索与调用链阅读，不默认安装插件、部署向量库或维护新知识系统。对高风险遗漏通过相关集成/回归验证补充，不将多查资料等同于业务验证。

## 4. 实施与最小修复

### 三个常用角色与按需专项测试

常用角色为方案分析、开发实现、独立审查；测试是贯穿开发的职责，复杂验证再按需启用专项测试角色。角色不等于固定Agent、会话或文档，不要求每次修改切换三次会话，也不因划分角色自动分派任务。

| 角色 | 必须考虑的内容 | 按需记录 |
| --- | --- | --- |
| 方案分析 | 合并需求分析与必要设计：先明确目标、使用者、范围、业务规则、正常/异常流程和验收，再结合现有工程确定复用点、修改路径、契约影响及关键取舍；涉及权限时覆盖未登录及无权限 | 沿用当前需求和方案位置，区分已确认与待决；长期设计决定进入当前架构，不重复背景，不为小修展开完整架构 |
| 开发实现 | 复核方案依赖和实际工程，拆成可运行验证的增量；沿用现有错误、授权、事务、配置和依赖模式，入口校验由服务端保证；完成本次必要自测 | 实际改动、验证证据、偏差及未完成；普通实现细节自行处理，重要规则、契约或技术路线变化回到方案澄清 |
| 独立审查 | 从需求、验收、方案、实际差异及相关调用链核查范围、正确性、兼容性与验证证据；不只阅读开发总结 | 有位置、触发条件及影响的问题，区分缺陷、待核实项和建议；明确审查基准、未覆盖项与重测范围 |
| 专项测试（按需） | 面向阶段验收、跨模块回归、端到端、性能、权限、并发或兼容性等需要系统覆盖的任务，设计场景并执行验证 | 是否启用由验证复杂度决定，是否形成完整测试文档由交付要求决定；日常局部修改不强制启用 |

文案、格式及简单可逆修改可由同一Agent完成并自查；一般功能和有业务风险的修复引入独立审查，高风险改动可在编码前增加方案审查。独立审查由不同于实现者的Agent或会话承担；同一Agent切换提示做检查属于自查，不能称为独立审查。没有独立审查条件时如实说明，不宣称已完成。

### 审查边界与依据

- 每项实质改动应能对应当前目标或必要依赖；排查夹带重构、额外能力、依赖升级及无关格式化，不要求为每行代码建立台账。
- 核实接口、字段、配置、依赖和业务规则的真实来源；推断与未决事项不能写成已确认事实。发现方案与工程不符时先核实，不盲目要求实现服从失效方案。
- 结合调用方检查前后端契约、权限、事务、缓存及异常路径，核对必要测试是否覆盖本次风险；构建、Mock和真实交互的证据不能相互替代。
- 对照实际文件及执行结果核实完成声明；证据不足列为待核实，个人偏好列为建议，不为凑问题扩大整改。
- 审查默认只读，不顺手修复、重构、构建或打包；需要执行验证时须在当前授权内明确其范围和副作用。问题交回开发修正，再按新差异复查；审查不能保证消除所有遗漏或模型幻觉。

### 执行顺序

1. 阅读相关需求、项目约束、代码和必要规范；修改前确认已有差异和本次边界。
2. 沿入口、调用方、业务逻辑、数据访问及测试核实触发条件、预期和实际，不能凭孤立片段打补丁。
3. 设计复用现有结构，明确影响和必要取舍；大任务按能运行验证的增量推进。需要计划时记录，简单改动不建计划文件。
4. 只修改必要路径，保持权限、事务、错误、配置与依赖契约。前后端都审查不等于两端都必须改；无问题的一端说明结论。
5. 开发按风险完成自测，再按上述角色规则审查最终差异；发现问题由开发修正，完成相关重测与复查。回补实际失效的文档与结果，有产物要求时按[delivery.md](delivery.md)完成。

有业务或状态风险的缺陷优先在修改前用针对性回归复现，再验证修复后通过；无法复现时说明证据限制。文案、格式及简单可逆改动做必要核查即可，不机械新增测试。原型明确未完成与未验证范围。

## 5. 验证与证据

- 日常必要自测由开发实现负责，审查方核对其覆盖与证据；启用专项测试不替代开发自测，未启用专项测试也不能省略关键验证。
- 从工程文件、Wrapper、CI和已有脚本确定命令，按受影响路径和风险选择静态、构建、逻辑、集成或交互检查。局部修改不默认前后端全套回归，也不能跳过已识别的关键风险或项目明确要求。
- 先核实测试访问的环境及副作用；只在授权范围执行，不为验证连接业务库或启动服务。空字符串、不存在的变量和禁用开关语义可能不同，须查看代码。
- 区分产品缺陷、夹具、依赖及环境问题。测试等待或夹具错误不代表问题已复现；纠正后重跑受影响检查，保留首次失败原因和最终结果。
- 分别报告通过、失败、错误、跳过和未执行范围；不同环境和开关的数量不能直接比较，历史报告不能代替本轮执行。
- 已有失败或不稳定测试须有证据，不能凭猜测归因。CI先读具体失败日志，修复本次回归；其余问题说明影响，不扩大整改。远端重跑须在已有授权内。
- 模拟网络、watcher、生命周期或定时器的测试只证明相应逻辑，不能扩写为真实框架调度、浏览器、权限或外部集成验收。
- 完成相关及项目要求的验证后不无理由重复或扩大测试。命令、范围、结果及限制在交付或已有项目记录中说明，不默认新建测试文档。

## 6. 恢复、交接与协作

- 接手或压缩恢复后核对最新指令、目标、允许/禁止操作和已完成证据；历史摘要、待办、PID和包号不是当前事实或授权。无法核实时先只读检查，只暂停依赖未决事项的工作。
- 当前目标仍有效就继续；用户的状态询问不等于替换任务。新指令明确改为只读或切换范围时更新边界，不能恢复旧实施任务。
- 长任务或确需交接时，用现有记录保存任务来源/范围、决定和证据位置、已完成/未完成、下一步及阻塞；结束时关闭。单份文档、讨论和小修不建立检查点。
- 简短说明重要发现、恢复后的当前目标与下一步，不输出整份上下文、逐条工具流水账或固定key=value协作日志；业务日志遵循后端规范。
- 其他任务需要接续时以当前文档和实际工程为依据，可复用合适会话或更换执行人，不依赖最初Agent永久负责。共享修改按当前任务划定写入方。
- 协调方核实实际差异、文件、测试与产物；收到消息或子任务宣称完成不等于验收。分派规则见[security.md](security.md)。

### 多角色接力与会话更新

方案分析、开发实现、独立审查不要求保留三个长期会话。各角色自行获取共同约束、相关模块和当前任务信息，不要求用户向不同角色重复解释背景或整理上下文包；独立性要求见第4节。

| 角色 | 必要上下文及核查 | 交接结果 |
| --- | --- | --- |
| 方案分析 | 总需求的相关范围、旧能力、共享规则及实际实现；主动查历史关联 | 本次范围、复用/修改点、关键取舍、契约影响和验收 |
| 开发实现 | 最新确认方案、相关源码/调用方/数据及项目约束；复核方案依赖是否仍成立 | 实际改动、代码/工作区基准、验证证据、偏差及未完成 |
| 独立审查 | 需求与验收、方案、明确的待审版本/差异及相关调用方；不只看完成总结 | 有证据的问题、影响、重测范围及未覆盖项 |
| 专项测试（启用时） | 验收标准、相关流程/契约、已有测试、待测版本与允许操作的环境 | 场景覆盖、真实结果、缺陷及未验证范围 |

- 项目资料记录共同事实，任务记录只保存本次范围、决定、代码基准和证据引用；不要为三个角色各复制一套项目历史。新发现的有效共同规则回补当前资料，不能只留在某次聊天或交接摘要中。
- 当前任务、代码/工作区或方案在交接后发生变化时，接手者重新比较差异，必要时更新方案及审查范围；旧审查结果不能自动覆盖新版本。同一范围仍由一个写入方修改。
- Agent主动识别会话污染信号：混用已废弃/已完成规则、反复重查已核实事实、无法说清当前目标及版本、摘要与源码冲突、无关工具输出持续堆积。先核实并清理当前任务事实；在需求/阶段结束、角色切换或干扰仍明显时提出换会话建议，不要求用户自行判断过期信息。
- 换会话前将必要状态回补到已有任务/需求记录：当前目标与授权、相关依赖/约束、决定来源、代码/工作区基准、验证、阻塞与下一步。接手者据此重新查实际工程，不能只信压缩摘要；不搬运整段聊天，也不按固定消息数量或猜测token余额强制换会话。
- 需要新会话而平台不能创建或尚未获得创建授权时，提供可直接转交的简短接续指令和资料路径，明确需要用户的唯一动作；不宣称已自动切换。当前明确任务不因“可能缺上下文”自行中断，缺口只影响相关依赖步骤。

## 7. 收尾

审查改动范围、调用契约、必要文档、验证及未完成项。方案、执行报告、问题记录和交接各担其责，历史与当前状态明确区分。回复按本轮实际产出组织；项目特别交付条件在适用范围内完成，不能把部分验证、产物生成或文档更新称为全部验收。
