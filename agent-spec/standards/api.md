# API 约定

已有项目的既有接口和新增接口均优先沿用现有 URL、返回体、HTTP 状态和错误码。本约定的格式用于新项目，或经确认建立独立契约的接口；通用校验和安全要求仍适用。

## 设计

- 接口表达业务能力，不直接暴露数据库表、实体或内部字段。
- 资源使用名词和稳定路径，例如 `/api/orders/{id}`；只在动作无法自然表达为资源变更时使用动词。
- 需要版本时使用明确前缀，例如 `/api/v1`，不通过随意改字段维持不兼容变更。
- 外部依赖由单独的集成层调用，并规定超时、失败处理和必要的重试范围。

## 请求与响应

成功和失败使用项目统一的响应结构，至少包含可判断结果的状态、面向调用方的消息和数据：

```json
{
  "code": "0",
  "message": "success",
  "data": {}
}
```

- 必填、长度、格式、范围和枚举在服务端校验。
- 校验错误、认证失败、无权限、状态冲突和系统故障要能区分。
- 明确 HTTP 状态与业务错误码的对应关系。成功使用适当的 2xx，参数错误、未认证、无权限、状态冲突与系统故障分别采用适当的 4xx 或 5xx；不默认将所有失败返回为 HTTP 200。已有契约需要兼容时遵循已确认方案。
- 错误码一旦对调用方发布就保持稳定，不为单个分支随意增加没有含义的编码。
- 响应不返回异常堆栈、SQL、内部地址或敏感数据。

## 安全与文档

- 认证和授权在服务端统一执行；敏感操作保留可追踪的操作日志。
- 接口说明与实现保持一致，至少包含参数、结果、权限和主要失败情况。
- 状态变化要说明允许的前后状态，以及重复请求时的结果。
- 重试仅用于可安全重复的操作，规定次数或时间上限；非幂等操作不得盲目自动重试。
