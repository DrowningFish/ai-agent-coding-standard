# Java / Spring 后端规范

本规范仅适用于项目确认使用Java/Spring时。以下版本是模板默认配置，项目明确的版本、构建与工具选择以project-rules和工程文件为准；其他技术栈保留通用质量原则，不机械套用本规范。

## 基础环境

- JDK 17。
- Spring Boot 3.x，选择仍受支持且兼容 JDK 17 的版本。
- Maven 或 Gradle 二选一；已有项目沿用现有构建工具。
- 依赖版本由构建文件统一管理，不在子模块随意覆盖。
- ORM、缓存、配置中心和注册中心沿用项目已有选择；新项目只在有明确用途时引入。
- 需要数据库持久化时优先使用MyBatis-Plus或项目已选定的JPA等持久化框架；不为简单CRUD另写一套JDBC访问。需要缓存时优先考虑Redis，需要分布式配置或注册时考虑Nacos或Eureka。组件按需引入，已有项目沿用稳定选择，实际采用及理由记录在项目架构中。

## 工程结构

- 使用标准构建目录，生产代码与测试代码分离。
- 模块和包按清晰业务职责组织，避免把无关内容堆入 `common`、`util` 或超大 Service。
- Controller 负责协议适配、认证上下文和输入校验，不承载核心业务。
- 业务逻辑、数据访问和外部集成保持明确边界；不为了层数而创建只有转发作用的类。
- 公共 API、数据库模型和外部契约变化必须先确认影响。

## 代码格式

源码使用 UTF-8。缩进为 4 个空格，不使用 Tab。每行不超过 120 个字符，超出时按参数、条件或链式调用换行，后续行比当前语句多缩进一级。

- 左大括号放在语句末尾，右大括号单独成行。`if`、`else`、`for`、`while` 和 `do` 必须使用大括号。
- 一行只写一条语句，不把多个赋值、判断或 `return` 压缩到同一行。
- 二元运算符和逗号后保留一个空格；左小括号内侧不加空格。
- 不使用星号导入。静态导入只用于少量常量和测试断言。
- 类中的顺序为常量、静态字段、实例字段、构造方法、公开方法、受保护方法、私有方法。
- 类名使用大驼峰，方法和变量使用小驼峰，常量使用大写加下划线，包名全部小写。布尔判断使用 `is`、`has` 或 `can` 前缀。
- 不把字面量直接散落在业务判断中。可复用的数值、状态和配置键定义为有名称的常量或枚举。
- 空集合返回空集合，不返回 `null`。需要表达可缺失的返回值时使用明确的业务结果或 `Optional`，但不把 `Optional` 用作字段或方法参数。

## 类、方法与常量注释

手写的类、接口、枚举、记录类型、方法、构造方法及常量均使用中文Javadoc，以 `/** ... */` 编写，放在声明和注解之前。公开、受保护、包内和私有方法，以及简单访问器、覆盖方法均适用，不以 `//` 或普通 `/* ... */` 代替声明注释。不手工修改第三方或生成代码补注释，已有项目只对本次新增或实质修改的内容应用要求。

- 第一句说明职责，并以句号结束。需要补充前置条件、副作用或失败方式时另起段落。
- 每个参数写 `@param`，类型参数有业务含义时说明其约束；非 `void` 方法写 `@return`，无参及 `void` 方法不虚构标签。需调用方处理的失败写 `@throws`，不罗列不可能发生的异常。
- 参数说明写清业务含义、允许为空与否，以及适用的单位、范围和格式；返回说明写清业务含义、空值/空集合含义、状态或数量口径，不只重复类型或参数名。
- 注释解释业务含义和约束，不重复方法名。例如不写“获取订单”，而写“按订单号返回当前用户可见的订单。订单不存在时返回空。”
- 私有方法及覆盖方法同样写明中文职责、参数和返回含义；可引用上层契约，但不能只写一个 `{@inheritDoc}` 而省略说明。
- 常量注释写明业务含义；涉及数量、时长、金额、状态、阈值时注明单位、适用范围和必要边界，不只复述名称。枚举项作为常量同样说明含义。
- 记录类型在类型Javadoc中用 `@param` 说明各组件的含义与约束；手写访问器仍需方法注释。测试类、测试方法及辅助方法同样使用中文Javadoc，说明测试意图及必要前置条件。
- 较长方法在逻辑分段、关键业务判断、批次/事务边界、特殊算法和异常恢复处补充简短中文注释，说明目的或原因。内部段落可用 `//`，不逐行翻译代码；方法职责过多时优先合理拆分，而不是靠大量注释掩盖复杂度。
- 修改行为时同步修改说明。不用注释掉的旧代码保留历史。

```java
/** 写入执行批次的起始条数，不代表每批独立提交事务。 */
private static final int DEFAULT_WRITE_BATCH_SIZE = 1000;

/**
 * 创建订单并冻结对应库存。
 *
 * <p>库存不足时不保存订单，也不部分冻结库存。
 *
 * @param command 已完成入口校验的下单命令，不能为空
 * @return 新建订单的编号
 * @throws InsufficientStockException 可售库存小于购买数量时
 */
public String createOrder(CreateOrderCommand command) {
    // ...
}
```

## 编码要求

- 优先使用构造器注入，依赖和可变状态必须明确。
- 在系统边界校验输入；业务失败使用项目统一且稳定的错误表达。
- 项目已有权限模型时，在服务端校验授权，不依赖前端隐藏入口。
- 不吞异常，不用 `catch (Exception)` 隐藏错误；补充上下文时保留原始原因。
- 事务范围尽量小，跨服务调用不依赖本地事务制造虚假原子性。
- 涉及重复请求、并发更新或消息消费时明确幂等和并发策略。
- 配置通过配置文件和环境变量注入，不在代码中写入密码、令牌或环境地址。
- 不把数据库实体或内部持久化结构直接作为对外接口契约。
- 涉及数据库时使用参数化查询，避免拼接用户输入；对可能增长的数据使用分页或明确上限，检查逐行重复查询。迁移说明兼容性、环境和恢复方案。
- 外部请求设置超时；重试仅用于可安全重复的操作，限定次数或时间。不可幂等的请求不盲目重试。
- 文件、连接和流及时释放；异步任务明确容量上限、取消和失败处理，不使用无界队列或无界并发。

## 数据库交互与批量处理

### 持久化框架与SQL位置

- 常规CRUD优先使用MyBatis-Plus的Mapper/条件构造器，或项目已有JPA Repository、派生查询、Criteria等能力。数据访问集中在Mapper/Repository等持久化边界，不散落在Controller和业务循环中。
- 需要手写关联查询、聚合、批处理或数据库特定SQL时，优先放入MyBatis Mapper XML或框架支持的独立映射文件；Java方法定义参数、结果和业务调用，不内嵌 `select ... from ...` 等原生SQL字符串或文本块。
- 不使用Java中的SQL字符串拼接、SQL常量类、MyBatis注解SQL、内嵌SQL Provider或JPA的内嵌原生SQL注解规避此要求。JPA优先使用框架查询能力，必要原生SQL使用外置映射；迁移DDL仍放项目迁移文件。
- XML等映射同样参数化。动态表名/列名只允许受控白名单，不把用户输入直接替换进SQL。映射参数名、结果映射、分页、权限过滤、租户/业务范围和乐观锁语义与Java契约保持一致。
- 批处理应优先通过既有持久化框架和映射实现，并核实实际SQL及往返；不能因为采用ORM就默认已经批量，也不能以性能为由随意把原生SQL搬回Java。涉及独立SQL文件加载时沿用框架机制，不自建复杂加载器。
- 既有项目使用JDBC等机制时不自动全库迁移；本次新增或实质修改优先遵循上述要求。确有框架能力不足或数据库特定限制时，先说明原因、影响及替代方式，由项目约定或用户确认例外，不自行扩大技术迁移范围。

### 后端铁律：增删改查优先批量，杜绝逐条往返

数据库交互必须先按集合设计，所有增删改查均适用。处理多条记录时，不得默认采用“遍历一条→查询/校验一条→写入一条→提交一条”的实现。单记录业务可执行必要单次操作，不为凑批次引入额外机制。

| 操作 | 优先方式 | 禁止的默认实现 |
| --- | --- | --- |
| 查询/校验 | 去重业务键后分批查询、JOIN或聚合，按业务键建立Map/Set并在内存校验 | 每条记录调用getById、exists、count或重复加载同一字典/基线 |
| 新增 | 批量校验后使用框架/驱动真实批写，核实唯一约束及重复请求语义 | 循环调用单条insert/save并逐条提交 |
| 更新 | 按相同更新条件/字段分组执行集合更新，或批量执行参数化更新 | 每条先查再改，不必要地重复查询及更新未变化内容 |
| 删除 | 明确权限与业务作用域后按条件或分批业务键删除，保留引用保护 | 为删除列表逐条查询、逐条delete，或为提速扩大删除范围 |

- 业务循环内只做内存计算、组装与校验，数据库调用移到循环外或批次边界。检查for/while、Stream、回调及被调用的Service/Repository，不能把逐条SQL藏进辅助方法；ORM懒加载触发的N+1同样违反此要求。
- 允许用于分页读取、IN分片或批写的批次循环，每次处理一个有界集合，而不是包装单条调用。处理N条记录时，交互随必要批次数及固定阶段增长；按业务依赖核实模型，不让可合并交互随记录数逐条增长。
- 先汇总并去重业务键，批量查询需要的字段，再用Map/Set关联；可复用的字典、规则和作用域数据在必要一致性边界内一次加载或批量取得，不对每条重复读取。
- 不能仅因业务需要逐条校验就逐条查库；应先批取必要数据再校验。确有无法集合化的跨记录依赖、锁或顺序约束时，先论证批量替代方式；例外须有已确认项目约定或明确确认，并说明范围、次数与一致性原因，不能自行以“特殊场景”放行。
- 仅名称含batch/saveAll不代表减少了数据库往返，须核查实际SQL与驱动执行方式；把单条操作异步并行执行仍是逐条交互，不能作为批量优化交付。
- 同一数据源内的集合变换优先评估JOIN、聚合、INSERT SELECT及按条件批量更新，避免全量搬到应用再逐条写回；保留权限、作用域、乐观锁、业务校验和审计语义，不为提速绕过它们。
- 空集合直接返回，不生成空IN；批量查询仍使用参数绑定。动态表名、列名须来自白名单，不用拼接用户输入替代批量参数。

### 批次与读取方式

- 无项目实测配置时，后台大数据扫描可从每批10000条读取、写入可从每批1000条批量执行开始评估；这些是可调整起始值，不是所有数据库的安全值或性能承诺。普通页面查询按页面大小和接口上限，不默认返回10000条。
- 查询页大小、IN参数数量、驱动fetchSize、写入执行批次和事务提交批次是不同参数，不复用一个batchSize统管。按行宽、绑定参数总量、SQL/报文长度、驱动限制、连接池、内存及锁持有时间调小，已有配置和实测结果优先。
- 大量ID查询分片时核实数据库参数/IN限制，多列写入同时计算总参数量。禁止把全部ID拼成巨大SQL，或为凑批次一次加载全部业务数据。
- 大表扫描使用稳定且唯一的排序键；优先评估键集分页、游标或流式读取，避免不断加深OFFSET。数据会变化时明确快照/一致性与断点规则，保证不漏读、不重复处理。
- fetchSize只是驱动读取设置，不等于业务分页或内存有界；核实游标、事务及驱动条件，分批消费后释放已处理对象和连接。不要一边标称流式读取，一边collect为全量List。

### 批量执行与事务提交分开决定

- 每1000条执行/flush一次不等于每1000条commit一次。要求整体原子的业务在同一事务内分批执行，全部成功后统一提交；不能为提速拆散审批、账务、库存或状态切换的一致性边界。
- 只有业务允许独立完成、部分成功可识别且可恢复时，才采用例如每1000条一个独立事务；明确检查点、幂等键、失败/重试范围及最终状态。不要在框架管理事务中私自调用连接commit或切换autoCommit。
- 核查驱动是否支持批处理以及实际往返，不为了批量默认升级依赖、打开未经验证的驱动选项或改成多语句拼接。复用预编译语句；框架需要时分批flush并释放持久化上下文。
- 不捕获批处理异常后仍报告全部成功，也不逐条自动重试整批。结合事务结果、批执行返回语义和业务幂等性确定受影响范围；成功计数不确定时明确标记，不将未知更新数当成精确行数。
- 更新/删除始终限定业务范围；批量乐观锁或条件更新核对预期冲突。批次按稳定顺序处理以降低锁竞争，死锁/超时重试有边界，不能用无限重试掩盖问题。

## 常见性能问题与实现约束

- 查询只取需要的列和范围；不为展示少数字段SELECT全部大字段，不在每页重复读取全量基线、重复COUNT或重新构建同一份昂贵上下文。确有需要的总数和跨页一致性不能直接删除。
- 对慢查询先看实际SQL、参数规模、执行计划和索引命中。避免在关键过滤列上随意套函数、隐式类型转换及无边界模糊匹配；索引结合过滤/排序和写入代价评估，不为每个字段盲目建索引。
- 列表匹配、去重和差异计算避免嵌套全表扫描；适合时建立一次索引映射，避免O(n²)。注意映射的内存成本，超大数据改用分段处理，不能为省查询无限缓存。
- 导入、导出和文件转换分段读取、校验、写出，避免反复解析同一文件、重复序列化或复制完整大对象；保留完整覆盖、审计及历史快照等业务必须的数据，不能把减量存储当作无条件优化。
- 优先减少无效工作和外部往返，再考虑并发。数据库任务使用有界线程池，按连接池余量和数据库能力限制并发；不对每行创建线程、滥用parallelStream或把阻塞任务塞进公共线程池。
- 不在持锁或长事务期间执行慢网络/文件操作；确需原子配合时评估阶段化或项目已有一致性模式。外部服务支持批量接口时优先聚合，不能批量时使用受限并发及超时，不默认无限重试。
- 缓存只用于有明确重复访问收益的数据，规定容量、期限、失效和一致性边界，不能用缓存掩盖错误查询或用过期数据完成权限/关键状态判定。不为一次请求引入新缓存组件。
- 热循环避免逐条INFO日志、全量对象输出及昂贵重复格式化；批任务保留开始、结束、分阶段进度、失败和汇总日志，不能为减少日志丢失关键证据。

### 性能验证与自检

单次功能/业务操作出现几十次数据库往返时，必须触发交互次数审查，沿入口至持久化路径统计并定位重复查询、N+1、逐条更新、隐式刷新及过碎事务，优先合并和减少往返；不能仅解释为“数据库慢”或通过加线程、加连接池、延长超时掩盖问题。“几十次”是排查信号，不是允许上限；大型任务合理分页/分批产生的次数应按数据规模、批次及阶段解释，不能为少次数改成无界SQL或破坏事务。

- 分别观测SQL执行次数、实际网络往返、执行批次数和事务提交次数；一次驱动批次可能执行多条SQL，不能把Mapper调用数或SQL条数直接当作网络往返，也不能只凭某一指标断言已优化。
- 对相关数据量验证交互增长方式，例如同一业务从少量增加到数百/数千条时，关联查询不再每条增加一次；实际往返、提交随必要批次增长。先记录合理预期，再用项目已有SQL统计、驱动日志、监控或针对性测试核实，避免为此默认新增监控组件或输出敏感SQL参数。
- 存在性能问题或改动交互策略时，交付说明优化前后数据规模、查询/批写/提交次数及耗时证据；未测明确说明。不能只凭方法名、代码看似简洁或本机小数据通过就宣称性能改善。

实现涉及批量或性能变化时，按风险核实：空数据、尾批不足、分批后结果一致、重复键、失败回滚/断点重试及并发冲突。关注实际SQL/远程调用次数、批次数、吞吐/耗时、峰值内存和锁等待，不能只凭使用batch方法或线程数增加宣称提速。

对比使用相同数据规模、业务语义和可比环境，记录配置及未覆盖范围；小修不机械做全面压测。项目特定批次、超时、连接池和验收口径填写在[project-rules.md](../project-rules.md)，不把起始建议写成已验证参数。

技术核查参考：[Spring JDBC批操作](https://docs.spring.io/spring-framework/reference/data-access/jdbc/advanced.html)说明批处理接口与驱动能力；[pgJDBC游标读取](https://jdbc.postgresql.org/documentation/query/)说明fetchSize生效依赖驱动与事务条件。实际使用仍以项目数据库、驱动版本和实测为准。

## 日志

统一使用 SLF4J API，由 Spring Boot 默认的 Logback 输出。需要输出日志的类声明一个日志对象：

```java
private static final Logger log = LoggerFactory.getLogger(OrderService.class);
```

不使用 `System.out`、`System.err`、`e.printStackTrace()` 或其他日志框架。消息使用占位符，不使用字符串拼接。

业务日志消息正文使用一行 `key=value` 文本，至少包含事件名和定位操作所需的业务标识。异常堆栈允许框架输出多行：

```text
2026-10-12T19:35:00.123+08:00 INFO  c.example.order.OrderService - event=order_created orderId=1001 userId=23
```

有请求上下文时加入同一个 `traceId`。异常只在最终处理位置记录一次，把异常对象作为日志方法的最后一个参数，让框架输出完整堆栈。

### 级别

- `ERROR`：当前操作失败，并且需要人工或上游处理。存在异常时必须附带原异常对象；没有异常时记录稳定失败原因，不为日志虚构异常。
- `WARN`：操作可以继续或已经降级，但结果偏离正常路径，例如重试、使用兜底数据或发现脏数据。
- `INFO`：记录关键业务操作、状态变化和最终结果；长耗时和批量任务记录开始。正常查询、校验和内部方法调用不逐次记录。
- `DEBUG`：补充定位问题必需且允许记录的参数、分支、中间结果和外部交互摘要，不要求每个方法记录进入和退出。

生产环境默认输出 `INFO` 及以上。排查问题时打开对应包的 `DEBUG`，不把 `DEBUG` 作为生产常开级别。

### 必须保留的关键日志

关键操作必须能够从日志还原结果与定位问题，不得因减少日志而删除这些信息：

- 应用启动完成和定时任务、消息消费的开始与结束。
- 创建、提交、取消、审核、支付等业务命令的最终结果，包含业务标识和成功、拒绝或失败原因；成功通常为 `INFO`，拒绝和失败按实际语义选择级别。
- 订单、库存、权限等关键状态的迁移，包含迁移前后的状态。
- 关键外部调用结束时的目标服务或操作名、结果、耗时和业务标识，不直接记录可能含凭据的完整 URL。
- 重试、降级、异常和最终失败：包含原因、次数或上下文，分别使用适当的 `WARN` 或 `ERROR`。

不在循环中为每条普通记录输出 `INFO`。批量任务输出开始、结束、总数、成功数和失败数；空数据任务仍输出结束和总数为零，不能静默消失。

关键操作的各条日志共享 `traceId` 或任务关联标识。业务结果在负责该操作的边界记录，调用链中不重复打印同一结果或异常。预期业务拒绝不一律记录为系统错误。需要安全审计的操作按项目审计要求保留，普通调试日志不能替代审计记录。

### DEBUG 的内容

仅在有助于定位问题时输出以下 `DEBUG` 信息：

- 明确允许记录的业务参数或摘要。
- 决定分支的条件和实际选择。
- 计算、匹配、库存占用和权限判断的中间结果。
- 外部调用的操作名、响应状态、错误码和必要的请求、响应摘要。
- 必要的结果摘要，不重复输出上层已记录的内容。

密码、令牌、私钥、证件号和完整支付账号即使在 `DEBUG` 中也不得原文输出，使用脱敏值或只输出是否存在。大文件和二进制内容只记录长度、摘要和标识。

采用明确允许记录的字段，不直接输出整个 DTO、请求体或响应体，也不依赖对象 `toString()` 自动脱敏。用户输入中的换行和控制字符必须安全处理，摘要应限制长度。昂贵的摘要计算或序列化仅在日志级别启用时执行。

```java
log.info("event=order_created orderId={} userId={}", order.getId(), command.getUserId());
log.info("event=order_status_changed orderId={} fromStatus={} toStatus={}",
        order.getId(), previousStatus, order.getStatus());
log.debug("event=order_pricing_summary orderId={} itemCount={}", order.getId(), itemCount);
log.info("event=inventory_sync_finished taskId={} total={} succeeded={} failed={} durationMs={}",
        taskId, total, succeeded, failed, durationMs);
log.info("event=payment_call_finished orderId={} operation={} result={} durationMs={}",
        order.getId(), operationName, resultCode, durationMs);
log.error("event=order_create_failed userId={}", command.getUserId(), exception);
```

## 测试

- 业务规则优先使用快速单元测试。
- 数据库、Spring 配置、序列化和外部契约使用有针对性的集成测试。
- 测试至少覆盖正常路径、边界条件和主要失败路径。
- 测试应可重复，不依赖执行顺序、真实生产服务或上一次运行遗留状态。
- 测试验证业务结果，不复制实现过程，也不只断言 Mock 调用。修复行为缺陷时优先增加可复现的回归测试，条件允许时确认修复前失败、修复后通过。
- 按实际风险覆盖权限与数据隔离、事务回滚、并发和重复请求、外部超时与失败；不涉及的能力无需套用场景。确认测试环境和数据，不用业务数据执行破坏性测试。

## 验证

先读取构建文件、Wrapper、CI 和现有脚本，再确定实际命令。优先使用工程 Wrapper，Windows 使用其对应脚本。按改动风险执行格式或静态检查、相关单元测试、必要集成测试和构建，并完成仓库明确要求的完整检查；不为每个任务固定执行 `clean` 或假定某个任务存在。

优先使用已有 formatter、lint 和静态检查；新增工具前核对与 4 空格、120 字符及项目规则的兼容性，不随意引入依赖。

记录实际命令、环境、结果及未覆盖范围。格式检查通过不代表业务正确，构建通过不代表运行或集成通过。依赖下载、网络、权限或服务问题与代码失败分开记录，不得宣称未执行的验证通过。
